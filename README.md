# pi-history

One history modal for [Pi](https://pi.dev). It recalls and searches previous prompts in a single Pi-drawn overlay rather than browsing in Pi's input bar, so your draft stays untouched until you confirm a record.

Targets Pi **1.5.2** on Linux and macOS. It is a Pi package written in TypeScript and loaded by Pi directly, with no build step.

> Do not load it together with another prompt-history extension (for example `pi-input-history`): both take over the input bar's history keys.

## Status

The bootstrap ([#2](https://github.com/ningw42/pi-history/issues/2)), fuzzy search ([#3](https://github.com/ningw42/pi-history/issues/3)), configuration with skim ([#4](https://github.com/ningw42/pi-history/issues/4)), the repo and global scopes ([#5](https://github.com/ningw42/pi-history/issues/5)), the complete, cached history source ([#6](https://github.com/ningw42/pi-history/issues/6)), skill invocation restoration ([#7](https://github.com/ningw42/pi-history/issues/7)), the preview pane with list rendering ([#8](https://github.com/ningw42/pi-history/issues/8)), the Up entry ([#9](https://github.com/ningw42/pi-history/issues/9)) and the real-Pi smoke suite ([#10](https://github.com/ningw42/pi-history/issues/10)) of the design in [#1](https://github.com/ningw42/pi-history/issues/1) are done. What works today:

- **Up**, with Pi's standard editor or a [compatible custom editor](#editor-compatibility), opens the history modal at Pi's native recall position: on an empty input bar, or with the cursor at the very start of the draft. As in Pi, Up elsewhere on the draft's first row first takes the cursor to its start, and the next Up opens the modal; on any other row (of a multi-line draft, or of a long first line that wraps) Up moves the cursor up, and while the autocomplete popup is open Up does what it does there (by default, moves through its list). If you have bound a key to Pi's `tui.editor.historyPrevious` action, that key opens the modal from anywhere in the draft. **Down** outside the modal is plain cursor movement.
- **Ctrl+R** (or the [configured](#configuration) search key) in the input bar, at any cursor position, opens the same modal.
- Both work while the agent is working, so a follow-up or steering prompt can be recalled at any time, and after `/new`, `/resume`, `/fork` and `/reload`. Another extension's input bar editor stays in place, with its own look and keys other than the history entry points; editors without both public cursor and autocomplete methods get search-key-only entry, as described below.
- The modal lists the prompts you typed, one row per unique prompt (its most recent use wins), at most the newest 5,000 (configurable). Multi-line prompts are shown as one row, their line breaks as `↵`, and a row too long for the terminal ends with `…`.
- Below the list, a **preview** shows the selected prompt with its line breaks intact, wrapped to the width, in up to four rows (fewer on a short terminal); `…` at its end means there is more. The line above the preview says when the prompt was last used, in local time, and in which directory (your home directory shown as `~`, and a long one cut from the left, so its project's name stays), so a prompt from another project is recognisable in global scope. With nothing selected (loading, no history, no matches, a failed search) the preview is empty.
- A prompt that began with a skill invocation is listed, searched and recalled as the command you typed, `/skill:name arguments`, not as the several-kilobyte skill body Pi stores: words that only occur in the skill's instructions never match, and Enter puts the command in the input bar, so submitting it runs the skill as it is now. Invocations of one skill with the same arguments are one record, even if the skill was edited in between.
- History is complete and fresh: a prompt you submitted seconds ago is there, even in an ephemeral `--no-session` run (and still there after `/new` or `/fork` in that run), and so are prompts on branches you abandoned and before a compaction.
- The modal opens at once and says it is loading while history is read. What was read from session files is kept in memory while Pi runs, so later opens read only session files that are new or have changed; a deleted session's prompts are gone at the next open.
- The modal always opens in **repo** scope: the prompts of every session started in the git repository you are in, at its top level or in any subdirectory, so starting Pi in a subdirectory still shows the whole repository's history. Outside a git repository, repo scope is the exact current working directory. Pressing **Ctrl+R** (the search key) inside the modal switches to **global** scope, every Pi session on the machine, and back. The query is kept, and the list is reloaded for the new scope with its best candidate selected. The title names the scope and the frame changes colour with it; the key hints name the scope the key switches to.
- The modal has a **query line**, which starts with whatever is in the input bar when the modal opens, by Up or by the search key. Editing it never changes your draft. With an empty (or whitespace-only) query the list is newest first. With a query, the list is ranked by [**fzf**](https://github.com/junegunn/fzf), or by [**skim**](https://github.com/skim-rs/skim) (`sk`) if you configure it: match quality first, recency second, so an old obvious match beats a recent weak one. The matcher's search syntax works (several terms, `'exact`, `^prefix`, `suffix$`, `!negation`, `a | b`).
- The best candidate starts selected and is the list's bottom row, the one nearest the query line, with the preview between them. **Up** moves to older (or lower-ranked) records, **Down** back toward newer (or higher-ranked) ones.
- The modal's bottom edge lists its keys: what the search key does (`ctrl+r switch to global`), then `↑↓ navigate`, `enter confirm` and `escape cancel`, or whichever keys your Pi keybindings give those actions. On a terminal narrower than 71 columns they wrap onto rows of their own above it, so none is lost.
- If nothing matches, the modal says so. If the matcher is missing or fails, the modal shows why; clearing the query still browses newest first.
- **Enter** replaces the whole draft with the selected record and puts the cursor at the end. Nothing is submitted.
- **Escape** closes the modal and leaves the draft, cursor and collapsed pastes exactly as they were.
- Confirm, cancel and list navigation follow your Pi keybindings (`tui.select.confirm`, `tui.select.cancel`, `tui.select.up`, `tui.select.down`).
- Session files are only read. The extension does nothing outside Pi's interactive (TUI) mode.

## Editor compatibility

Pi's standard editor and `CustomEditor` subclasses expose public `getCursor()` and `isShowingAutocomplete()` methods, so both entry points work normally. A custom editor missing **either** method gets **search-key-only** entry: neither Up nor `tui.editor.historyPrevious` is intercepted for history, on an empty or nonempty draft. Those keys stay with the editor, including its cursor movement and autocomplete navigation and completion. The configured search key still opens the modal, with the usual confirm/dismiss behaviour and precedence (even if you configure it to Up or the previous-history key). The wrapper neither reads private state nor replaces the custom editor to obtain these capabilities.

For editors with both methods, **history entry wins collisions outside autocomplete**: Up at the start of the draft and the previous-history key open the modal even if another editor action shares the key. For example, Up also bound to Tab completion opens history rather than starting completion; `historyPrevious` bound to Ctrl+W opens history rather than deleting a word. An open autocomplete popup keeps its own navigation, cancellation and completion keys. The configured search key retains its separate, highest priority while the input bar has focus.

For every composed editor, **Pi-fed in-bar history is disabled**: prompts Pi submits or loads are dropped at `addToHistory`, so they cannot be recalled into the input bar. This does not clear history a custom editor privately preloaded or maintains independently; such independent in-bar history is outside the supported integration.

## Install

Searching needs [`fzf`](https://github.com/junegunn/fzf) on your `PATH` (any recent release; developed against 0.72 and 0.75), or [`sk`](https://github.com/skim-rs/skim) if you [configure](#configuration) skim instead (tested with 4.7 and 5.9). Without the matcher the modal still browses newest first, and says that the matcher is missing whenever there is a query (including one started from the draft).

Install the latest `main` from Git (no npm publication or build needed):

```sh
pi install git:github.com/ningw42/pi-history
```

For a pinned release, append a published tag, for example `git:github.com/ningw42/pi-history@v0.1.0` once that release exists. Tags stay pinned when Pi updates packages; choose a newer tag explicitly to upgrade.

From a development clone:

```sh
npm ci --ignore-scripts
pi -e ./src/index.ts            # try it once
pi install /path/to/pi-history  # or add it to your Pi settings
```

## Configuration

Everything works without configuration. To change a setting, create `pi-history.json` in Pi's agent directory: `~/.pi/agent/pi-history.json`, or `$PI_CODING_AGENT_DIR/pi-history.json` if you set that variable. Every setting is optional:

```json
{
  "matcher": "sk",
  "matcherCommand": "~/.local/bin/sk",
  "searchKey": "ctrl+t",
  "recordLimit": 10000
}
```

| Setting | Default | Meaning |
|---|---|---|
| `matcher` | `"fzf"` | The program that ranks results for a query: `"fzf"` or `"sk"` (skim). |
| `matcherCommand` | the matcher's name, found on `PATH` | The executable to start: a command name looked up on `PATH`, or a path. A leading `~/` means your home directory; any other relative path (such as `bin/sk`) is relative to the agent directory that holds this file, never to the directory Pi was started in. |
| `searchKey` | `"ctrl+r"` | The key that opens the history modal from the input bar and switches its scope inside it, in [Pi's keybinding syntax](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/keybindings.md#key-syntax) (for example `"ctrl+t"` or `"alt+h"`), in any case. Escape takes no modifiers: Pi never recognizes `ctrl+escape` and the like. It takes precedence over every Pi binding on the same key while the input bar has focus. Inside the modal, a key that also acts as confirming, cancelling or moving the selection (`tui.select.confirm`, `tui.select.cancel`, `tui.select.up`, `tui.select.down`), through your Pi keybindings or because your terminal sends it as one of those keys (Ctrl+M as Enter, Ctrl+[ as Escape, without the Kitty keyboard protocol), keeps that action, so the scope cannot be switched: the modal's bottom edge says so, and Pi warns you once. |
| `recordLimit` | `5000` | How many unique prompts, newest first, the modal holds at most in each scope. A positive integer. |

The file is read at every session start (Pi's startup, `/new`, `/resume`, `/fork` and `/reload`); run `/reload` to apply changes right away. If it cannot be read or is not a JSON object, Pi shows a warning and every default applies. An invalid value or an unknown setting is ignored with a warning that lists every problem, and the other settings still apply. Each warning is shown once: later session starts, `/reload` included, repeat it only if the problems have changed.

## Design

### Vocabulary

- **History modal**: the single Pi-drawn overlay through which all history browsing and searching happens.
- **Entry point**: a way into the modal: the **Up entry** (Up where Pi would start recalling history) or the **search entry** (Ctrl+R, configurable).
- **Draft**: the text in Pi's input bar when an entry point fires.
- **History record**: one unique user-typed prompt, after restoration, with the time and working directory of its most recent use.
- **Scope**: which sessions records are drawn from: **repo** (the git repository containing the current working directory, or exactly that directory outside a repository) or **global** (every session).
- **Matcher**: the external program that filters and ranks records for a query: `fzf` (default) or `sk`.
- **Skill envelope**: the expanded form in which Pi stores an explicit `/skill:name` invocation: the skill's instructions wrapped in a `<skill …>` block, followed by the arguments.
- **Restoration**: turning a skill envelope at the very start of a prompt back into `/skill:name arguments`.
- **Confirm / dismiss**: the two ways the modal closes, with a record or without changing anything.

### Modules

| Module | File | Responsibility |
|---|---|---|
| Entry point | `src/index.ts` | Wires the modules together from the configuration; inert unless Pi is in TUI mode. |
| Configuration | `src/config.ts` | Loads and validates the optional configuration file, falling back to defaults per setting, and describes every problem in one message. |
| Key syntax | `src/key-syntax.ts` | Pi's keybinding syntax, parsed in one place: whether a configured key is one Pi recognizes, and whether two keys are one key to Pi's key matching (any case and modifier order, `esc` as `escape`, `return` as `enter`). |
| Editor integration | `src/editor-integration.ts` | The only module that knows about Pi's editor. Wraps the input bar's editor to install the entry points, and applies a confirmed record to the draft. |
| History modal | `src/history-modal.ts` | The overlay component. Owns the scope, loading state, the query line, the result list and selection; handles keys; renders the list, the preview of the selected record and the key hints. Resolves with "confirmed text" or "dismissed" and **never writes to the input bar**. |
| History source | `src/history-source.ts` | Given a scope and the current session context, returns history records newest first, restored, de-duplicated and limited to the record limit, from the live session in Pi's memory and from Pi session files. Hides session enumeration, session-file parsing, repository-root resolution and caching. |
| Skill restoration | `src/skill-restoration.ts` | A pure text-to-text function: a prompt that begins with a skill envelope becomes `/skill:name arguments`; any other text is returned as it is. No I/O, no state. |
| Matcher adapter | `src/matcher.ts` | Given a query, newest-first records and a cancellation signal, returns the matching records ranked, or a typed failure. Hides every difference between fzf and sk, process handling, the NUL-delimited transport, environment scrubbing and exit-status interpretation. |

### Decisions

- **The entry points are handled by wrapping the input bar's editor, not by `pi.registerShortcut`.** The wrapper sees every key before Pi does, so Ctrl+R (or the configured key) takes precedence over any Pi binding on the same key while the input bar has focus, and only the editor knows the cursor position and autocomplete state the Up entry depends on. It is installed only in TUI mode, so nothing is registered in print, JSON or RPC mode. A registered `ctrl+r` shortcut would also be registered outside TUI mode, and Pi would report it at startup as a conflict with the `/resume` picker's rename binding.
- **The wrapper is installed synchronously at `session_start`, before any I/O, and never again.** Replacing the editor later would dismiss a selector the user opened in the meantime (for example `/model`). History is read only when the modal opens, and again whenever its scope is switched.
- **The configuration file is read synchronously right after the wrapper is installed**, in the same `session_start` handler. The wrapper looks its configured parts (search key, matcher, history source) up when a key arrives, so installing needs no configuration and does no I/O, yet the configuration is always in place before the first key. Outside TUI mode the file is not read. The file lives in the agent directory reported by Pi's `getAgentDir()`, so `PI_CODING_AGENT_DIR` is honoured.
- **Pi 1.5.2 loads the extension afresh at every session start**: `/new`, `/resume`, `/fork` and `/reload` reset the extension UI (removing the wrapper), re-import the module (its loader disables jiti's module cache) and call its factory again. So the file is re-read each time, and nothing kept in the module or the factory survives. To warn only once, the last reported problem is remembered in process-wide state (a `Symbol.for` key on `globalThis`): a problem is reported when it is new or changed, at any session start including `/reload`; fixing the file forgets it, so making the same mistake again is reported again. The history cache lives in process-wide state for the same reason.
- **Configuration problems never disable the extension.** An unreadable file, invalid JSON or a non-object means every default; an invalid value means that setting's default; an unknown setting (often a misspelt one) is ignored. All of them are listed in one warning, so a typo is noticed instead of silently ignored.
- **The search key is validated against Pi's documented key syntax** (modifiers `ctrl`, `shift`, `alt`, `super`, each at most once, then a known key, in any case) **and Pi's key matching**, because an unrecognised key would match nothing and leave no way to open the modal. Pi's matcher rejects Escape (or `esc`) with any modifier outright, so those are invalid too; every other modified key has a Kitty or modifyOtherKeys form, even if a given terminal cannot send it. Like Pi's own keybindings, any valid key is accepted, even one that shadows typing.
- **The wrapper composes with an editor factory configured by another extension**: an extension loaded earlier that installs its own editor keeps it, with its rendering and any working-status embedding. The wrapper takes the editor that factory builds, intercepts the available entry points' keys in front of it and blocks Pi's history feed as described below; all other keys stay with that editor. Without one, it falls back to Pi's `CustomEditor` with the working-status indicator embedded in its border, as Pi's own editor has it.
- **Up and previous-history entry require both public cursor and autocomplete capabilities.** The state comes from `Editor.getCursor()` and `Editor.isShowingAutocomplete()`, public methods Pi's standard editor and `CustomEditor` subclasses have. Pi's editor contract (`EditorComponent`) does not require them. If either method is missing, neither Up nor `tui.editor.historyPrevious` opens the modal, even on an empty input bar: both stay with the composed editor, preserving its editing and completion. The configured search key still opens the modal and keeps its normal precedence; confirmation and dismissal work as usual. There is no private-state inspection, replacement editor or guess that an empty draft means no popup. Standard Pi editors are unaffected by this compatibility gate.
- **The Up entry uses Pi's native start-of-draft position**: the key bound to `tui.editor.cursorUp`, pressed with the cursor at line 0, column 0. Pi 1.5.2 recalls on Up only from the first visual row when the draft is empty or the cursor is in column 0, which is that one position; anywhere else on the top row Up first moves the cursor to the line's start, and that step is kept. The key bound to `tui.editor.historyPrevious` (none by default), which Pi uses to recall from anywhere, opens the modal from anywhere. An open autocomplete popup keeps every key Pi's editor gives it first, whichever keys your keybindings make them: closing it (`tui.select.cancel`), moving through it (`tui.select.up`, `tui.select.down`, `tui.select.pageUp`, `tui.select.pageDown`) and completing with its selection (`tui.input.tab`, `tui.select.confirm`). These rules apply only when both public capabilities are present, and after checking the configured search key.
- **Outside autocomplete, history entry wins a collision with another editor action.** Up at its entry position and `tui.editor.historyPrevious` open the modal before the editor handles the key. Thus Up also bound to `tui.input.tab` opens history rather than starting completion, and `historyPrevious` bound to Ctrl+W opens history rather than deleting the previous word. This is a deliberate precedence policy, tested with representative collisions, not a copy of Pi's entire internal action ordering. Popup-owned keys still win while autocomplete is open; the configured search key has its separate priority over both.
- **Pi's `addToHistory` feed is suppressed for every composed editor.** Pi hands the input bar's editor every prompt it submits or loads through that method; the wrapper drops those calls, including for editors missing either public capability. This blocks recall of Pi-fed prompts, not history an editor privately preloaded or maintains independently: the wrapper does not inspect or clear that history, which is outside the supported integration. On Pi's standard editor the in-bar history stays empty and the keys that would start recall open the modal instead; Down and `tui.editor.historyNext` only step back through a recall already started, so Down is plain cursor movement and `historyNext` (none by default) does nothing but close the autocomplete popup.
- **The modal keeps focus while the agent works.** Confirmed against Pi 1.5.2: nothing in its streaming path moves focus. Pi's TUI focuses an overlay when it is shown and gives focus back when it is hidden; Pi focuses the input bar itself only on user actions (at startup, when an editor factory is installed, when a selector, login or reload box closes, and when a dialog shown in the input bar's place closes). That last one can happen under an open modal, for example when another extension's confirmation, shown while the agent works, closes; the keys then reach the input bar, and the wrapper hands them to the modal, as it does while the modal is opening or closing (below).
- **The working directory recorded in each session header is the authority**, not the storage directory name: two directories such as `/a/b` and `/a-b` share one storage directory name. Pi records absolute directories; a session recording a relative one, or none, is never in repo scope, though it is still in global scope.
- **Text blocks of one user message are joined with no separator**, the way Pi's interactive mode joins them for display and native history. Images and other non-text blocks are ignored, and a message with no text is no prompt.
- **Every user message counts**: those on branches you abandoned (with `/tree` or `/fork`) and those before a compaction are still in the session file, and still history. A prompt that was typed is history.
- **A prompt that begins with a skill envelope is restored to the command that was typed.** Pi 1.5.2 stores `/skill:name arguments` as `<skill name="NAME" location="FILE">`, a `References are relative to DIR.` line and a blank line, the skill's instructions, `</skill>`, and then, if arguments were typed, a blank line and the arguments. That becomes `/skill:NAME`, or `/skill:NAME ARGUMENTS` with the arguments exactly as stored, line breaks included. DIR is the skill's base directory: Pi's own loader sets it to FILE's directory, but a skill supplied as an object through Pi's SDK can name any, or none, so DIR is not compared with FILE.
- **Restoration is conservative: anything unexpected is shown as stored.** Only an envelope at the very start of a prompt is restored, so a prompt that quotes skill markup later on is left alone. A prompt is also shown as stored when the name could not be typed back as a command (anything but letters, digits, `.`, `_`, `:` and `-`, starting with a letter or digit), FILE is not absolute, the line after the opening tag is not a `References are relative to DIR.` prologue followed by a blank line, no closing tag on a line of its own is followed by the end of the text or by a blank line and arguments, or the end of the body is ambiguous. The body ends at the first such closing tag, where Pi's own skill-block parser would stop: the first `</skill>` line after the prologue's blank line, the instructions' first line included, that is followed by the end of the text or by a blank line and arguments. (Pi writes nothing else after its own, so a `</skill>` line in the instructions followed by more instructions cannot end it.) If the text after that closing tag holds a line that is exactly `</skill>`, the body may have ended there instead (a skill whose instructions contain that line), and the arguments cannot be told apart. Pi's parser itself is not used: it takes the first closing tag even then, and trims the arguments. The work is linear in the prompt's length, however large the skill body.
- **Restoration does not consult the skills loaded now.** History shows what was typed; whether the skill still exists, or has changed, is Pi's concern when the command is submitted. The fork change this is modelled on (`pi-input-history`'s "recall skill invocations as /skill:name arguments") restored only skills currently loaded from the recorded file, which in global scope would leave most invocations from other projects as multi-kilobyte bodies.
- **Records are restored inside the history source, before de-duplication and caching**, so the list, the matcher's input and the confirmed text all hold the restored command, and two invocations with the same arguments are one record even if the skill's instructions changed in between. The process-wide state's key is versioned with what its records hold, so after an update and `/reload` no prompt an older version cached unrestored is served. What an older version kept is taken over instead, for each session storage as it is first loaded: the prompts of ephemeral sessions that ended earlier in the process, which are on no disk, are restored and de-duplicated again (each command at its most recent use); what it read from session files is dropped, and the files are read again.
- **The live session is read from Pi's memory**, from the session manager's entries at every load (on opening the modal and on each scope switch), so a prompt submitted seconds ago appears at once, as do the prompts of an ephemeral (`--no-session`) session, which never reach disk. It is in both scopes, wherever the session was started. Its session file is still read like any other, because a second Pi process continuing the same session (`pi -c` in another terminal) appends to it too; the copies of a prompt in memory and on disk are one record after de-duplication.
- **An ephemeral session's prompts outlive it, for the life of the Pi process.** They are on no disk, and in a `--no-session` run Pi's `/new` starts a fresh in-memory session and its `/fork` rewrites the session to one path, so they would otherwise vanish (Pi's own in-editor history keeps them). So when a session ends (`session_shutdown`: `/new`, `/resume`, `/fork`, `/reload` or quitting), an ephemeral one's prompts are kept in process-wide state with the session storage it would have been saved in, and later loads include them in both scopes, as while it ran. A persisted session's prompts are not kept: its file stays the authority, so deleting it still removes them from history.
- **Keys that arrive while the modal is opening or closing belong to the modal.** Pi mounts the overlay asynchronously and gives focus back to the editor before the result arrives, so keys from the same terminal input batch (for example a fast Ctrl+R or Up then Enter, or a double Enter) would otherwise reach the editor and submit the draft the modal is replacing. Once the modal has closed, such keys are dropped: they neither edit its query nor start a search.
- **The session storage** is the current session's. A custom session directory, which holds every session and is then the only directory read, is configured with `PI_CODING_AGENT_SESSION_DIR` or else the `sessionDir` setting (Pi's precedence), wherever it is, even inside `<agent dir>/sessions`. A persisted session reports the directory it actually uses, and that wins: the configured one is custom; another one directly inside `<agent dir>/sessions` means Pi's default layout, one directory per working directory, all of which are read; any other is custom too (as with a `--session-dir` flag). Only a `--session-dir` flag naming a directory directly inside `<agent dir>/sessions` is taken for the default layout: extensions cannot see the flag, and Pi's own test for the default layout compares against its private encoding of the working directory, which the extension does not depend on. An ephemeral (`--no-session`) session reports none, so the configured directory applies, else Pi's default layout. A `--session-dir` flag is not visible to extensions in an ephemeral session, so `--no-session --session-dir <dir>` does not read `<dir>`; to browse a custom directory's history in an ephemeral session, set `PI_CODING_AGENT_SESSION_DIR` or the `sessionDir` setting instead.
- **Sessions are found by listing the storage directories, not through Pi's session-listing API.** `SessionManager.list` and `listAll` parse every line of every file they list, to build summaries the extension does not use. The repo scope must look in every storage directory, because each subdirectory of a repository has its own. So the first line of each `*.jsonl` file, its session header, is read on its own for the recorded working directory, and only the files in scope are read in full. The storage rule above is what honours a custom session directory, the reason #1 gave for using Pi's API.
- **What is read from session files is cached for the life of the Pi process**, in process-wide state (Pi re-imports the module at every session start), so `/new`, `/resume`, `/fork` and `/reload` keep it. It is kept per session storage. Every load still lists the storage and checks each file's device, inode, size and modification time, all at once; a file whose four are unchanged is served from memory, and only new or changed files are read. A file's header is read once per change of the file; its prompts are read once its session is first in scope, so opening repo scope never reads other directories' sessions in full. A deleted file is dropped from the cache at the next load, and its prompts are gone. A file that cannot be read is skipped and tried again at the next load, rather than remembered as empty. Pi appends to a session file as you work, which changes its size, so the live session's file, and that of a session another Pi process is running in, is read again in full at the next open. No warm-up runs at session start: the first open reads what it needs, behind the loading state.
- **Loading never blocks Pi.** Files are read asynchronously, one at a time. The work done on Pi's main thread (parsing prompts, keeping each text's newest use, ordering the records) runs in time slices of about 8 ms and yields to the event loop between them, so keys and rendering are handled while a large history loads, cold or cached, and a scope switch or closing the modal stops a load at its next slice. Within a file only the lines that can hold a user message, those containing `"user"`, are decoded and parsed, found by scanning the file's bytes rather than decoding and splitting all of it; each parsed line is turned into its prompt at once, so its images are not kept. Inside a JSON string, such as a tool's text output, the quotes are escaped, so tool output costs next to nothing; a line whose JSON objects hold the word as a key or value, such as a tool call's arguments, is parsed too, and yields nothing. Ordering newest first sorts small runs of records and merges them pairwise, each merge stopping at the record limit, since sorting 100,000 records at once would itself hold the thread for tens of milliseconds. Parsing one line cannot be split, so one huge prompt still costs its parse at once.
- **The repository is found the way git finds it, without running git**: walking up from the current working directory, the top level is the first directory whose `.git` is a git directory, or a file (a linked worktree's or a submodule's) whose `gitdir:` line names one. A git directory passes git's own test (`is_git_directory`): its `HEAD` is a symbolic link into `refs/` (even to an unborn branch) or a file holding `ref: refs/…` or an object id, and its common directory (named by `commondir` in a linked worktree's) has searchable `objects` and `refs` directories. An invalid `.git`, such as an empty directory or one holding only `HEAD`, does not stop the search; as with git, the directories above it are still searched. (Pi's footer accepts any `.git` holding `HEAD` and stops at an invalid one.) git itself is not run: `git rev-parse --show-toplevel` resolves symbolic links, so a repository reached through one (such as macOS's `/var`, really `/private/var`) would no longer match the working directories Pi records.
- **A repository checked out inside another is a separate repository.** A session recorded in a linked worktree, a submodule or any other clone inside the repository (for example in `.worktrees/fix`) belongs to that repository's repo scope, not the enclosing one's, and separate worktrees of one repository are separate repositories wherever they are. Top levels are checked on disk at each load, so the sessions of a nested worktree that has since been deleted fall back into the enclosing repository.
- **Every open starts in repo scope**; the scope is not remembered. **Switching scope** cancels the previous scope's loading and any search and shows the loading state; then the kept query is matched against the new scope's records (an empty query lists them newest first), and the best candidate is selected. Nothing loaded or matched for the previous scope is shown after a switch. Inside the modal the search key is checked before the query line's editing keys but after the confirm, cancel and navigation keys (`tui.select.*`), so the modal can always be closed and navigated. If the search key also acts as one of those, that action keeps it and the scope cannot be switched; rather than advertise a switch that never happens, the bottom edge then reads, for example, `ctrl+r move selection up (scope switch unavailable)`, and a warning names the conflicting keybinding and how to resolve it. The check matches the input the search key actually sent to open the modal against the keybindings in effect then (Pi reloads them after `session_start` on `/reload`), so it reflects both your keybindings (a `searchKey` of `"up"`, or `tui.select.up` rebound to Ctrl+R) and your terminal: without the Kitty keyboard protocol Ctrl+M arrives as Enter and Ctrl+[ as Escape, which count as conflicts, while with it they are keys of their own and switch scope. It runs at every open and warns once per conflict. A modal the Up entry opens has no input from the search key, so there the check compares keys instead: a list keybinding that has the search key itself (in any case, modifiers in any order, `esc` as `escape` and `return` as `enter`, as Pi's key matching reads them) is a conflict, while one the terminal alone causes is only seen, and warned about, at an open by the search key.
- **The scope is shown three ways**: the title names it (`History · repo`, `History · global`); the frame and title take the theme's `borderAccent` colour in repo scope and its `warning` colour in global scope; and the key hints on the bottom edge start with the key and the scope it switches to (`ctrl+r switch to global`).
- **The layout, top to bottom**: the title, the list, a rule naming the selected record's last use, the preview, a rule, the query line, and the key hints on the bottom edge. The best candidate is the list's bottom row, the one nearest the query line, and the list extends upwards, so Up moves both to older (or lower-ranked) records and visually away from the query; the preview sits between them, as #1's layout orders them. The modal is anchored to the bottom of the terminal, so the query line stays in place.
- **The preview has a fixed height**: four rows, padded when the record is shorter, so the list does not jump as the selection moves between records of different lengths. The list and the preview share the terminal's rows less the modal's others (five, and any rows of key hints) and eight left to the conversation: the preview takes up to four, giving up rows below 20 terminal rows, down to one, before the list goes below three; the list takes the rest, at most 15. The overlay may take 80% of the terminal's rows (Pi drops the lines beyond, the query line and key hints first), so on a terminal too short for that the conversation gives up its rows, then the preview its last one, then the list all but the selected record's: the query line, the key hints and the selection stay in view down to 8 rows at 71 columns or more, and about a row more for each row the key hints wrap onto (9 rows at 60 columns, 10 at 40). The terminal's height is read at every render, so a resize re-lays the modal out; the selection is scrolled into view, and as many rows as there is room for are filled, so growing the terminal again brings back the better candidates below the selection.
- **The preview shows the record as the editor will hold it**: its lines broken where Pi's editor breaks them (LF, CRLF or a lone CR), tabs as four spaces, each line wrapped to the width with Pi's own wrapping (which never splits a wide character); a muted `…` ends the last row when more does not fit. The last use is the record's local time (`2026-11-01 09:02`, independent of locale) and working directory, the home directory shown as `~` (only a directory at or below it, not one that merely starts with its name); either is left out when the session did not record it, rather than showing 1970 or an empty directory. A directory too long for the line is cut from the left (`…/nested/project`), because its end names the project.
- **List rows** collapse each line break, with the whitespace around it, into ` ↵ `, and tabs into spaces, and are cut to the width with `…` by Pi's `truncateToWidth`, which never splits a wide character. There is no match highlighting: neither matcher reports match positions in filter mode. The selected row is drawn in the theme's `accent` colour, the others in the default one.
- **Rendering does no more work for a long record than for a short one, except across a long run of whitespace, where it does linear work.** Pi renders the modal at every key, and wrapping all of a 4 MB prompt takes about 330 ms, collapsing all of it into a row 30 to 80 ms. Both work on a prefix of the record, doubled until it is enough, and show exactly what the whole record would. A row collapses a prefix until it overfills the width, and a prefix never ends inside a run of whitespace: the run is read to its end, because a line break anywhere in it collapses all of it into one `↵`. Each run is matched once and tested for a line break, rather than matching the whitespace around a line break, which backtracks through a long run without one at every position (quadratic: half a second a render for 20,000 trailing spaces). The preview wraps whole each line that ends within the prefix, and of a longer line a prefix that fills the rows needed (one more than shown, to tell whether there is more): Pi wraps greedily, ending each row where the next word does not fit, so the word the prefix cuts short changes only the row that holds it, the prefix's last. Characters of several code units (an emoji family is eleven) and whitespace that wrapping drops take more doublings, but never more of the record than the line. So a long whitespace run within the row's width, or in a line the preview reaches, costs time linear in its length: rendering a prompt ending in 20,000 spaces takes 2 to 4 ms, in half a megabyte of them about 65 ms (mostly Pi's wrapping), against well under a millisecond for a short one.
- **The key hints follow Pi's keybindings**: each list action is named by the first key bound to it, in Pi's hint style (`↑↓` for the arrow keys, as Pi's own selectors write them), and left out if it has none. The search key's hint (or a conflict notice in its place) comes first. With the default keys they all fit on the bottom edge from 71 columns; on a narrower terminal they wrap onto rows of their own above it, as many hints to a row as fit and a hint too long for a row wrapped by words, so every hint is shown whole, and the layout makes room for those rows.
- **Recalled text goes through Pi's editor**, which stores CRLF/CR as LF and tabs as four spaces, as it does for typed and pasted text. Text typed, pasted or edited in Pi's input bar never contains those characters, so only text stored without passing through the editor is affected: RPC and SDK prompts, extension input transforms, and expanded prompt templates or skills.
- **The draft is the starting query, verbatim**, so the matcher's search syntax applies to it: a draft that begins with `!` or `'`, or contains ` | `, is read as matcher operators. Two exceptions: the query line is Pi's single-line text input, which cannot hold a line break, so a multi-line draft's line breaks become spaces, and a collapsed paste counts with its content, not its `[paste #1 …]` marker. The query is one command-line argument, so a paste larger than the operating system allows for one (about 128 KiB on Linux) cannot be searched and shows "Search failed". A whitespace-only draft or query counts as empty: nothing to match, so no matcher process runs. Because fzf and sk separate terms on spaces only, a line break inside a query would be part of a term; with spaces instead, a multi-line draft's lines are matched as separate terms and the search is looser than the matcher given the exact multi-line text.
- **The query line is Pi's own `Input` component**, so it edits like the rest of Pi and follows your editing keybindings. The draft is put into it as a bracketed paste, because `Input` has no public way to place the cursor and a paste leaves it at the end.
- **The matcher runs as a filter, never interactively**, started directly with an argument list (no shell), with records NUL-delimited on its standard input newest first, so multi-line prompts survive. Results are mapped back to records by text, which is unique after de-duplication. A record containing a NUL cannot be delimited and is never matched. Both matchers rank by match quality first and break ties by input order, which is recency; sorting is left on:
  - fzf: `fzf --filter=<query> --read0 --print0 --scheme=history`.
  - sk: `sk --filter=<query> --read0 --print0 --tiebreak=score,index`. Never skim's `--scheme=history`: unlike fzf's, it ranks input order ahead of match quality, so the newest weak match would win.
  - The query is attached to `--filter=` rather than passed as the next argument: sk reads a separate `-foo` as an option and fails, so a draft starting with `-` could not be searched.
- **Your matcher defaults cannot change the ranking**: `FZF_DEFAULT_OPTS`, `FZF_DEFAULT_OPTS_FILE`, `SKIM_DEFAULT_OPTIONS` and `SKIM_OPTIONS_FILE` are removed from the matcher's environment (`--no-sort` there would otherwise list results in recency order).
- **Only the latest query's results are shown.** A query edit waits 50 ms, then starts one matcher run; any earlier run is killed and its output discarded, so a slow search never replaces a newer one. Closing the modal kills a running search. Until the new results arrive the previous list stays on screen but cannot be confirmed: Enter does nothing while the list is out of date, so typing a query and Enter in one input batch never confirms a record the query does not match. Each new list selects its best candidate.
- **The "no match" status (1, for both fzf and sk) is a result, not an error**: the modal shows "No matches". A missing matcher is reported as not found, by its configured command; any other failure to start it (for example one that is not executable, or a query too long for the command line), any other exit status, and the matcher being killed by a signal are reported, an exit status with the matcher's first line of error output. A query containing a NUL character (only possible by pasting one) cannot be passed to the matcher and is reported too. There is no built-in fallback matcher.
- **The record limit is applied after de-duplication**, keeping the newest unique records, so it bounds what the modal holds and what is sent to the matcher.

## Development

Development and CI require **Node 26.x** (`.node-version`), npm, **`git`**, and both **`fzf`** and **`sk`** on `PATH`: the matcher adapter tests run the real fzf and sk and fail, rather than skip, without them, and two scope tests create repositories with `git init`. The Nix shell provides both (sk 4.7 from the pinned nixpkgs). CI installs fzf from each runner's package manager and sk from the pinned upstream release 5.9.0, checking the archive against a SHA-256 recorded in the workflow, because package managers ship skim releases years apart. The Node major is selected explicitly, not through a moving `latest` alias; the Nix lockfile pins the development package's exact version. The committed `package-lock.json` is the authority for JavaScript dependencies.

```sh
npm ci --ignore-scripts
npm run check       # typecheck and the non-PTY tests; also used by CI and the Git hook
npm run typecheck   # tsc, no emit (includes the PTY suite)
npm test                  # concurrent functional tests, then isolated performance checks
npm run test:functional   # functional tests only, concurrent files in separate processes
npm run test:performance  # performance checks only, one file at a time
npm run test:pty          # real Pi 1.5.2 smoke suite; Linux/macOS, requires tmux, fzf and sk
```

`npm test` runs two mandatory phases in sequence: **functional tests run concurrently**, then **performance checks run one file at a time** (`--test-concurrency=1`), with each file isolated in its own process. Functional tests use `test/**/*.test.ts`; the four wall-clock responsiveness and scaling checks live in `test/performance/**/*.perf.ts`, deliberately outside that glob. Their assertions and timing limits are unchanged: only their scheduling differs. Timing those checks alongside other files' large fixtures and child processes caused intermittent failures, so they run after the functional processes have exited, not concurrently with them. CI and the Git hook still use `npm run check`, which includes both phases. Neither phase is retried or optional; the individual commands are for focused development. These remain wall-clock checks, so unrelated machine load can affect them; run performance investigations on an otherwise idle machine.

`npm run check`, `npm run typecheck`, `npm test`, `npm run test:functional`, `npm run test:performance`, `npm run test:pty` and `npm run release:check` reject runtimes other than stable Node 26.x, with instructions to enter `nix develop` or select Node 26. The guard runs inside the commands, not through pre/post lifecycle hooks, so `--ignore-scripts` does not bypass it.

This is a **development policy**, not a restriction on Pi's runtime. The extension still loads inside whichever runtime runs Pi, including Bun; there is no Node 26 check in extension code. The existing `engines.node >=22.19` compatibility declaration is unchanged. CI tests Node 26 only; Bun and older Node runtimes are not verified by this suite.

Installation scripts are deliberately disabled: this source-only extension needs no build, and its development dependencies work without lifecycle scripts. No `devEngines`, `engine-strict`, `preinstall` or `prepare` gate imposes Node 26 on Pi's Git-package installation; dependency installation itself is intentionally not subject to the development guard.

### Real-Pi pseudo-terminal smoke suite

After `npm ci --ignore-scripts`, run **`npm run test:pty`** on Linux or macOS with **Node 26**, **tmux**, **fzf** and **sk** on `PATH`. `nix develop` provides those tools; otherwise install tmux through your package manager (for example `apt install tmux` or `brew install tmux`) and the matchers described under [Install](#install). No Python, native npm build, credentials or globally installed Pi is needed.

The suite runs the actual CLI shipped by the pinned `@earendil-works/pi-coding-agent` development dependency and requires its reported version to be **1.5.2**. Missing Pi, tmux or either matcher is a failure, never a skip. All five scenarios run once with each real matcher: Up/Enter recall without submission; Ctrl+R draft search, scope toggle and Escape with the cursor intact; `/model` opened immediately after startup and again across completion of a dismissed history load, then filtered and used to select a model; another extension's editor retaining its appearance and key; and a stored skill invocation recalled as its command.

Each scenario owns a private tmux server and socket, a fresh home, agent directory, session storage and working directory under `/tmp`. tmux supplies the real controlling PTY **and** terminal emulation: assertions read the current screen and hardware cursor, not an ANSI-stripped transcript or private editor/overlay fields. Screen waits are bounded and show the final screen on failure. The server and fixture directory are removed after the scenario, including on assertion failures; your existing tmux sessions are not used.

The Pi child gets an allowlisted environment with no inherited credentials or `NODE_OPTIONS`, empty `auth.json`, disabled resource discovery, no tools/MCP, `--offline`, disabled telemetry/version checks and Node's network permission withheld. Filesystem writes are restricted to its fixture directory. Node's permission model is a safety net, not a sandbox for hostile native code or child executables; the suite runs only the pinned Pi and your trusted installed tools. A test-only extension intercepts and records any accidental prompt submission before model dispatch, which fails the test. Its keyless static model catalog makes `/model` usable without credentials; either model-dispatch method also fails the test. Nothing queries a model.

The selector scenario also exercises the asynchronous-work hazard without inventing a startup scan: production deliberately has none. A test-only extension holds one full `readFile` of the synthetic session after the native read finishes, restores the filesystem method immediately, and announces the held read in the terminal title. The test dismisses the loading history modal, opens `/model`, then releases the read with a consumed Ctrl+G. Since dismissal already aborted this tiny load, its next time-slice/record check rejects without more I/O; the modal's promise handlers discard that result before a check-phase callback acknowledges completion in the footer. The selector must still hold its query and accept filtering/selection afterward. Shutdown also releases the barrier. No fixed observation sleep, private Pi state or production testing hook is used.

The skill fixture is generated by Pi itself: its public `AgentSession.steer()` expands a synthetic skill into the queue without starting an agent run, `clearQueue()` retrieves it, and `SessionManager` writes it to a synthetic session. The real CLI then searches and recalls that stored envelope. No handwritten expansion or private Pi method is used.

This separate command keeps the cross-platform extension-boundary suite usable on Windows and the Git hook lightweight. CI runs both `npm run check` and `npm run test:pty` on Linux/macOS; Windows runs only the former. To run every suite locally, use `npm run check && npm run test:pty`.

### Optional Nix shell and pre-commit hooks

```sh
nix develop          # Node 26, fzf, sk, tmux, Git, pre-commit, actionlint and nixfmt

pre-commit run --all-files
```

Entering `nix develop` generates the ignored `.pre-commit-config.yaml` link; it does **not** install npm dependencies or modify Git hooks. Use `pre-commit uninstall` to opt out.

The installed hook uses Nix store paths, so commits can also be made from outside the shell. Run `nix develop` again after updating the flake. The shell leaves an unrelated pre-commit configuration untouched.

The hook runs `npm run check` when source, tests, release scripts or Node configuration change, formats Nix files, and lints workflow files. Hooks are a local convenience, not an enforcement boundary: non-Nix contributors can run the npm commands directly, and PR CI is authoritative. If a formatter changes a file, review and stage it before retrying the commit.

`flake.lock` pins the Node/tooling environment for x86-64/ARM64 Linux and Apple Silicon macOS (the systems exposed by the pinned `git-hooks.nix`; Intel Mac and Windows contributors can use npm directly). This deliberately stays a **dev shell**, not a Nix package for the extension: Pi loads TypeScript directly, and duplicating npm dependency packaging would add little value. `git-hooks.nix` shares the same nixpkgs input.

```sh
nix fmt              # format flake.nix
nix flake check      # sandboxed Nix formatting and GitHub Actions lint checks
nix flake update     # explicitly refresh Nix inputs; review and commit flake.lock
```

`nix flake check` is a local convenience, not a CI job. It excludes npm checks because its sandbox has neither network access nor `node_modules`; CI runs the npm checks directly. Local `.pi/` agent state, generated hook configuration and Nix result links are ignored.

### CI and releases

Every PR and push to `main` runs `.github/workflows/ci.yml`: typechecking and tests on **Linux, macOS and Windows**, each with **Node 26**, read from `.node-version` (also used by the release job), with fzf installed through apt, Homebrew or Chocolatey, and with sk 5.9.0 from its checksum-verified upstream release. The runners are `ubuntu-latest`, `macos-latest` and `windows-latest`, using their default architectures; Windows uses amd64/x64. Linux and macOS also install tmux and run the real-Pi PTY smoke suite. Nix and workflow lint checks remain local only. Actions use explicit release tags (such as `v7.0.1`, not a floating major); Dependabot proposes monthly action updates. Tags are easier to read but can be moved upstream, unlike commit pins. To make these checks mandatory before merging, enable a GitHub branch ruleset for `main` and require the CI jobs (workflow files alone do not enforce merge policy).

Distribution remains Git-only: `package.json` is `private` to prevent accidental npm publication. Pi reads the existing `pi.extensions` entry point from the checkout and supplies the host packages declared as peers. There is no bundling, npm token, uploaded tarball or compiled release asset. GitHub provides its usual source archives.

To release:

1. On a normal PR branch, run `npm version patch --no-git-tag-version` (or choose `minor`, `major`, or an explicit stable version). This updates both `package.json` and `package-lock.json`. Commit both files and merge the PR after checks pass.
2. Tag the merged commit from an up-to-date `main` and push the tag:

   ```sh
   git switch main
   git pull --ff-only
   version=$(node -p 'JSON.parse(require("node:fs").readFileSync("package.json", "utf8")).version')
   git tag -a "v$version" -m "v$version"
   npm run release:check -- "v$version"
   git push origin "v$version"
   ```

3. `.github/workflows/release.yml` reruns the same CI suite for the tagged commit. Only after it passes, the release job checks that the stable `vX.Y.Z` tag matches both version fields in the lockfile and `package.json`, points at the checked-out commit, and is contained in `origin/main`. It then creates a GitHub release with generated notes using the built-in `GITHUB_TOKEN`. Only this job gets `contents: write`. Re-running the job leaves an existing release unchanged.

For the first release, the existing `0.1.0` can be tagged after this setup is merged; no artificial bump is needed. Prerelease tags are not supported yet. Published tags are immutable by convention: fix a bad release with a new version instead of moving its tag. A tag is installable by Pi as soon as it is pushed, even if the GitHub release checks later fail—those checks gate the GitHub release, not Git access to the ref. Generated release notes live on GitHub; this setup does not maintain a `CHANGELOG.md` for Pi's in-app update notices.

### Tests

The tests load the real entry point against a fake Pi API and UI context, with Pi's real editor and text-input components. The fake mirrors Pi's overlay lifecycle: the overlay is mounted asynchronously, and closing it gives focus back to the editor before the result arrives. It also mirrors how Pi starts a session (at startup and on `/new`, `/resume`, `/fork` and `/reload`): it removes the installed editor wrapper, calls the extension's factory again and then emits `session_start`. It cannot re-import the module the way Pi does, so extension code keeps no module-level state. History comes from synthetic session files in a temporary agent directory (`PI_CODING_AGENT_DIR`), written either as one linear conversation or entry by entry (for branches, compactions and content blocks), and from a fake live session whose entries the fake session manager reports, so no real prompt history is read. Starting a session after startup first emits `session_shutdown`, as Pi does, and may replace the live session's entries, as `/new`, `/resume` and `/fork` do. The history source's process-wide state outlives a harness, but it is kept per session storage, and every harness has its own temporary directory, so no test sees another's. Cache tests observe it at the boundary: a file made unreadable but otherwise unchanged is still listed (served from memory), while an appended, added or deleted file is reflected at the next open. Responsiveness (`test/performance/history-source.perf.ts`) is observed the way a user notices it: while a 100,000-prompt (about 50 MB) history loads, cold and then cached, a key is pressed every 5 ms, and every key must be handled within 100 ms (parsing it all at once held keys back about 300 ms), with the letters typed during "Loading history…" in the query line. Git repositories are mostly synthetic too, laid out as git leaves them: a `.git` directory holding `HEAD`, `objects` and `refs`; for a linked worktree, a `.git` file pointing to a git directory inside the main repository's (with `HEAD` and `commondir`); for a submodule, a relative `gitdir:`. Two tests use the real `git init` instead (with inherited `GIT_*` variables removed, so running from a Git hook cannot touch this repository), tying the synthetic layout to git's. The harness refuses to run when the temporary directory is inside a git repository, because every test directory would then share one repo scope; point `TMPDIR` elsewhere.

Tests assert on what a user sees: the input bar's text and cursor, its rendered lines (with an embedded working status or an autocomplete popup), and the rendered overlay lines (the title, the list rows, the last use, the preview, the query line and the key hints) and the colours of the frame, the title and each list row. `test/modal-rendering.test.ts` covers the layout as a whole (the best candidate's row relative to the query line), multi-line and very long records at narrow widths, wide characters and characters of many code units (every rendered line exactly as wide as the modal), whitespace wider than a row, the last use (in another time zone too, and a long directory on a narrow terminal), the key hints under rebound keys and wrapped at 60 and 40 columns, and a terminal resized while the modal is open, down to 8 rows and back (every line within 80% of the rows, the query, hints and selection in view). One test renders 40 generated records (runs of whitespace, every kind of line break, emoji, combining accents, CJK, long words) at three widths and requires each row and preview to be exactly what collapsing or wrapping the whole record gives, so the prefixes rendering works on never show. The harness's time zone is UTC unless a test sets `TZ`, so times are the same on every machine (Node applies a change of `TZ` on every platform, Windows included). In `test/performance/modal-rendering.perf.ts`, a record of 4 MB, on one line or many, must render in under five times as long as a short one (with a 2 ms floor for timer noise), and one ending in 20,000 spaces, with a line break after them or none, in under 24 times as long as one ending in 2,500 (linear work takes about 8 times as long, the quadratic matching it replaced about 64); wrapping all of it takes about 330 ms and collapsing all of it into a row 30 to 80 ms, against well under a millisecond for a short record. The one allowed exception is a narrow set of checks at the extension's external boundaries, for behaviour that has no visible output: prompts handed to Pi for submission ("nothing is submitted"), what the extension registered or installed with Pi, and whether an editor was installed other than synchronously at session start ("registers nothing outside TUI mode", "installed once"), the session files on disk ("never written"), and what the matcher process is given and whether it was killed. Tests never assert on the extension's private state.

The harness (`test/harness.ts`) always puts a scripted stub matcher (`test/fixtures/stub-matcher.mjs`) on `PATH` as `fzf` and `sk`, so on Linux and macOS the extension-boundary tests never reach a real matcher. The stub records its arguments, environment and input, replies with scripted output (chosen by the query and, optionally, by a record the input must hold, so one scope's run can be told from the other's), exit status, error output and delay or ends by a signal, and records whether it outlived its delay (that is, was not killed). The process contract each matcher must honour (exact arguments and NUL transport, environment scrubbing, the no-match status, a missing executable, a failure status with its first error line) is one suite in `test/fuzzy-search.test.ts`, run once per matcher from a row of fixture data. The matcher adapter is also tested on its own against the real fzf and sk (`test/real-matchers.test.ts`), with both programs' default-option variables and files set to options that would break the ranking: ranking on the fixture from the fuzzy-matching investigation, newest-first ties, search syntax, queries starting with `-` or `=`, and multi-line round trips. Skill restoration is also tested on its own (`test/skill-restoration.test.ts`), as a table of stored texts and what they restore to, because its edge cases are many and it is pure. The functional suite checks that 4 MB records are restored whole; `test/performance/skill-restoration.perf.ts` times the same fixture shapes at 0.5 and 4 MB: the larger must take under 24 times as long as the smaller (linear work takes about 8 times, quadratic about 64) and under 250 ms. Both use `test/fixtures/skill-records.ts`. The functional file also checks a stored invocation end to end: the list row, the matcher's input (which holds no word of the skill body) and the confirmed draft, and one record per command across an edited skill. It also checks an update by `/reload` from a version that kept prompts as stored: the process-wide state that version leaves behind (keyed and shaped as `main` at 5fa1da4 kept it) is set up before the extension loads, and the modal must list its ended ephemeral sessions' prompts restored, in both scopes, while its cached session files are read again; the assertions are still on the list. The configuration tests (`test/configuration.test.ts`) write the file into the harness's temporary agent directory, which the harness hands to Pi through `PI_CODING_AGENT_DIR`, so the user's real configuration never applies. The 50 ms debounce has no test: runs it would save are killed before the stub starts, so it is not observable at the process boundary.

The entry points are tested in `test/up-entry.test.ts` (Ctrl+R in `test/ctrl-r-modal.test.ts`). The fake wires the editor as Pi does: it gives it an autocomplete provider (Pi's own `CombinedAutocompleteProvider`, completing the files below the current directory), so Tab opens a real completion popup (and tests rebind its cancel and completing keys to Up), and it hands the editor every prompt submitted and, at each session start, the live session's prompts, as Pi does for its in-bar history, so a test that no key recalls a prompt into the input bar would fail if one did. Other extensions can be loaded ahead of this one: one installs a `CustomEditor` subclass with a key and a rendered line of its own, another an adapter around Pi's own editor that offers only Pi's editor contract, either public cursor/popup method, or both. The missing-capability cases cover empty and nonempty Up/previous-history input without a modal or Pi-fed recall, real popup navigation and completion, and configured-search-key confirmation and dismissal (including cursor preservation). Representative collisions outside autocomplete verify history entry over Tab completion and word deletion, without mirroring Pi's internal precedence table. Pi's working status is embedded the way Pi embeds it, in an editor that declares it embeds one. Keys can be sent to the input bar under an open modal, as when Pi focuses it there. The fake records each editor factory installed other than synchronously inside a `session_start` handler, which is when Pi would dismiss a selector opened in the meantime. To hold history loading open while keys are pressed, the current directory is made a git repository whose `HEAD` is a named pipe: resolving the repo scope reads it, and blocks until the test writes it; then it becomes a regular file. Named pipes need POSIX, so those two tests are skipped on Windows.

On Windows the stub uses `.cmd` launchers, which Node will not start without a shell, and the extension never uses one: tests that need the stub to answer are skipped there, and tests that open the modal with a draft may start the fzf CI installs, without depending on its outcome. The POSIX read-permission tests (an unreadable session file, and the cache serving or retrying one) are skipped on Windows (and for root), as are the tests for an fzf without execute permission and for a query too long to start fzf with; malformed-session coverage runs everywhere. The Windows job exercises the extension-boundary suite, not the real Pi terminal executable; only Linux/macOS run the real-Pi smoke suite.
